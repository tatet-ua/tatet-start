# mentor-site

Подготовка проекта, сборки, ошибки выкладки — [references/hosting.md](references/hosting.md).

## Всегда

- **Стоп** означает: дождаться, пока студент или ментор сделает действие сам или скажет «да» в чате.
- Сайт называется своим `name` во всех вызовах; адрес — `<name>-<студент>.tatet.app`.
- Свой домен к сайту подключает только ментор, через MCP его не подключить.
- Значения переменных не вставлять из файлов в чат: секреты — `site_env_generate` или скриптом; после любой правки
  переменных — `site_deploy`.
- Выкладок не больше 10 в час на аккаунт: перед `site_deploy` убедиться, что изменение готово.
- `site_delete`, `site_db_detach`, `db_delete` — **стоп**, только после «да» студента: это необратимо.
- Push в репозиторий — после «ок» студента.

## Перед началом

1. **Стоп:** студент добавляет коннектор: название `tatet.mentor`, адрес `https://mentor.tatet.app/mcp`, и входит
   через Tatet Auth почтой, которую знает ментор.
2. `me` отвечает аккаунтом студента и лимитами. Отказ «нет доступа» или «нет почты» — **стоп**, нужен ментор.
3. `gh auth status` — вошёл студент, у учётки есть доступ к репозиторию сайта.
4. Код сайта в ветке на GitHub, последний коммит запушен.

## 1. Подготовка проекта

Выбрать сборку: `railpack` (по умолчанию), `static`, `nixpacks` или `dockerfile` — по справочнику. Приложение
слушает `0.0.0.0` и порт, который будет указан в `site_create` (по умолчанию 3000, для `static` — 80).
docker-compose, диски и свои сети на хостинге запрещены: несколько сервисов — один Dockerfile и база аккаунта.
Локально `build` проходит.

## 2. Создание

1. `site_create`: `name`, `repo`, `branch`, `build_pack`, `port`.
2. **Стоп:** две команды `gh` из ответа (ключ доступа к репозиторию и вебхук) меняют настройки репозитория
   студента — запускать после его «да».
3. `site_deploy`: до него ничего не собирается.

Проверка: `site_status` → `running:healthy`; `curl -sI https://<name>-<студент>.tatet.app/` → 200 (или 302 у сайта
со входом). Не поднялся — `site_logs`, причина, правка, одна новая выкладка.

## 3. Обновления

Push в ветку выкладывает сайт сам. Проверка после первого push: в `site_status` новая выкладка, на сайте новая
версия.

## 4. Переменные (по необходимости)

`site_env_set` для обычных значений, `site_env_generate` для секретов (значение показывается один раз);
секреты, которые не нужны сборке, — с `runtime_only`. Затем `site_deploy`. Проверка: `site_env_list` — имена на
месте.

## 5. База (по необходимости)

`db_create` → `db_status` до `ready` → `site_db_attach` (сайт получает `DATABASE_URL`) → `site_deploy`. Схему базы
применяет само приложение при старте: база снаружи закрыта, с локальной машины к ней не подключиться. Проверка: запись, сохранённая на сайте, на месте после повторной выкладки.

## 6. Вход на сайте (по необходимости)

`site_auth_enable` → встроить вход по краткой инструкции из ответа (PKCE, без секрета) → `site_deploy` →
`site_auth_grant` на каждого пользователя. Проверка: выданный пользователь входит, остальные получают отказ.

## Итог

Студенту: адрес сайта, что push выкладывает сам, что подключено (база, вход). Свой домен — попросить ментора;
аналитика — скил `site-analytics`, когда сайт откроется по своему домену.
