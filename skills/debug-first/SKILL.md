# debug-first — причина до виправлення

## Залізне правило

```
НЕМАЄ ВИПРАВЛЕНЬ БЕЗ ВСТАНОВЛЕНОЇ ПРИЧИНИ
```

Лагодження симптому — це не лагодження. Особливо застосовувати, коли виправлення «очевидне», коли терміново і
коли попередні спроби не спрацювали.

Метод однаковий для коду, контенту й ігор: **симптом → гіпотези → перевірка → причина → виправлення → доказ**.
Приклади з трьох областей — у кінці.

## Фаза 0. Чи не траплялося це вже

Дешево і часто закриває питання одразу. База знань — `$TATET_WIKI`:

- `wiki/patterns/` — граблі й прийоми, що траплялися щонайменше у двох проєктах: чи не описано там цей стек,
  сервіс, платформу;
- `wiki/projects/<проєкт>.md`, розділ «Граблі» — що вже ламалося в цьому проєкті;
- `wiki/decisions.md` — чи не ухвалено рішення, яке пояснює поведінку (порт, схема, обхід, правило оформлення);
- `raw/sessions/` — пошук за ключовими словами помилки в логах сесій цього проєкту;
- `AGENTS.md` проєкту — розділ про граблі або відомі проблеми, якщо є.

Знайшов — застосовуй відомий діагноз і скажи: «це вже було, джерело таке-то». Це і є граблі: повторна помилка з
відомим діагнозом.

## Фаза 1. Дослідження причини

**До будь-якої правки:**

1. **Прочитати помилку цілком** — увесь stack trace, номери рядків, коди; у контенті — повідомлення сервісу
   цілком (Search Console, журнал доставки розсилки), в іграх — консоль рушія. Не прогортати. Часто відповідь уже
   там.
2. **Зібрати факти** — що мінялося останнім: `git status`, `git log --oneline -5`, `git diff`; без git — історія
   версій у CMS, журнал змін налаштувань сервісу, попередня збірка гри. Чи працювало це раніше.
3. **Прочитати справжній код або справжню сторінку** за шляхами з помилки — не здогадуватися про вміст.
4. **Перевірити межі** — які тут зовнішні залежності і яка з них могла віддати не те: сервіс, база, кеш, змінні
   оточення, порт, домен, пісочниця інструмента; у контенті — джерело, посилання, версія правила площадки,
   налаштування CMS, DNS-записи пошти; в іграх — версія рушія, налаштування сцени, збережений стан.

Відповідь на виході фази: **де саме** ламається (файл:рядок, конкретна сторінка, конкретна межа системи).

## Фаза 2. Відтворення

- відтворити стабільно й назвати точний сценарій («POST на X з тілом Y → 500», «лист на адресу в Gmail → немає ні у
  Вхідних, ні у Спамі», «рівень 3 з чистого збереження → двері після боса закриті»);
- звузити до мінімального випадку: прибрати все, що не впливає;
- якщо відтворити не вдається — це окремий факт: сказати прямо, не домислювати причину.

## Фаза 3. Гіпотеза, перевірена до правки

Сформулювати одним реченням: **«X відбувається тому, що Y»**.

Потім придумати **найдешевшу перевірку** гіпотези, яка не міняє логіку: лог, `curl`, читання запису в базі,
вимкнення однієї ланки, перевірка значення змінної оточення, «Перевірка URL» у Search Console, заголовки
отриманого листа, вивід лічильника в консоль гри, `Test-Path` з іншого оточення.

Перевірити гіпотезу → тільки після підтвердження писати виправлення.

Не більше **двох** сліпих спроб «поміняю й подивлюся». Після другої — обов'язкова ізоляція (звузити область,
додати логи, перевірити ланки по одній).

## Фаза 4. Виправлення і закриття

1. Мінімальне виправлення, що усуває причину, а не симптом.
2. Не ламати сусіднє — перевірити те, що працювало поруч до правки.
3. **Довести** (принцип «готово — це доказ»): відтворити початковий симптом і показати свіжим виводом, що його
   більше немає. Самоперевірка автора доказом не вважається: для нетривіальної правки перевіряє агент
   `tatet-start:verifier` з чистим контекстом (скіл `agent-mode`).
4. Незворотне на виправленні — публікація, відправка, деплой, зміна DNS, видалення — робить людина або оркестратор
   з «ок» власника (принцип 4).
5. Сформулювати запис для логу сесії: `**[назва]** — що неочікувано зламалося + діагноз + обхід`, і назвати її тип
   за словником:
   - **граблі** — уже траплялося, діагноз був відомий (знайшлося у фазі 0); позначити «знову, як у <джерело>»;
   - **підводний камінь** — прихована властивість середовища, про яку не можна було знати заздалегідь;
   - **пастка** — механізм поводиться неочікувано, але передбачувано, коли знаєш;
   - **відома проблема** — дефект сервісу чи бібліотеки, який обходять, а не лагодять.
6. Граблі, що повторилися в другому проєкті, — кандидат у `wiki/patterns/` (заводить `kb-ingest` за логом);
   рішення з неочевидною причиною — у `wiki/decisions.md` тим самим шляхом.

## Червоні прапорці — стоп, повернись у фазу 1

| Думка | Реальність |
|---|---|
| «Мабуть, справа в кеші» | Це гіпотеза без перевірки. Перевір |
| «Поміняю й подивлюся» | Утретє поспіль — ти не налагоджуєш, ти вгадуєш |
| «Тут очевидно, що …» | Прочитай код і вивід. Очевидне часто не те |
| «Перезапущу — раптом пройде» | Якщо пройшло, причина лишилася і повернеться |
| «Оберну в try/catch» | Це глушіння симптому, а не виправлення |
| «Терміново, ніколи розбиратися» | Систематичне налагодження швидше за метання |
| «Проблема в бібліотеці» | Спершу доведи, що твій виклик коректний |
| «Пошуковик просто не любить цю статтю» | Це не причина, а відмова її шукати. Перевір індексацію |
| «У мене в оболонці файл є» | Інструмент агента може жити в пісочниці; перевір з оточення, де симптом |

## Приклади: той самий метод у трьох областях

**Код — API віддає 500.**
- Симптом: `POST /api/orders` з порожнім полем `comment` → 500, з заповненим → 201.
- Гіпотези: (а) валідація не пропускає порожній рядок; (б) колонка в базі `NOT NULL`; (в) падає шаблон листа-
  підтвердження.
- Перевірка: лог сервера — `null value in column "comment" violates not-null constraint`.
- Причина: форма шле `null` замість порожнього рядка, а міграція зробила колонку обов'язковою.
- Виправлення: дозволити `null` у колонці (або підставляти `""` на вході — що відповідає задуму).
- Доказ: той самий запит з порожнім `comment` → 201, запис у базі є; запит із заповненим полем, як і раніше, → 201.

**Контент — стаття не ранжується.**
- Симптом: стаття опублікована три тижні тому, за цільовим запитом у пошуку її немає взагалі, навіть на дальніх
  сторінках.
- Гіпотези: (а) сторінки немає в індексі; (б) в індексі, але канонічною вказано іншу адресу; (в) запит перехоплює
  власна старіша стаття.
- Перевірка (найдешевша першою): Search Console → «Перевірка URL» — «виключено тегом noindex»; у коді сторінки
  `<meta name="robots" content="noindex">`.
- Причина: шаблон чернетки в CMS ставить noindex, під час публікації прапорець не зняли.
- Виправлення: зняти noindex у налаштуваннях статті, надіслати запит на індексацію; у шаблоні чернетки — пункт
  чеклиста публікації.
- Доказ: повторна «Перевірка URL» — «сторінку можна індексувати»; через кілька днів сторінка є в індексі. Позиції
  в пошуку — наступне питання, яке розбирається окремо тим самим методом.

**Контент — лист не доходить.**
- Симптом: розсилку в сервісі позначено «відправлено», частина отримувачів на Gmail листа не бачить навіть у
  Спамі.
- Гіпотези: (а) лист відхилено через автентифікацію домену (SPF, DKIM, DMARC); (б) адреси в списку з помилками;
  (в) сервіс розсилки не відправив.
- Перевірка: журнал доставки сервісу — статус «bounced», код `550 5.7.26` (неавтентифікований лист); у заголовках
  тестового листа собі — `dkim=fail`.
- Причина: після переїзду домену на новий DNS не перенесли DKIM-запис.
- Виправлення: додати DKIM-запис із налаштувань сервісу розсилки. Зміна DNS — дія в зовнішній системі: робить
  власник або агент після його «ок».
- Доказ: тестовий лист на Gmail — у заголовках `dkim=pass` і `dmarc=pass`, у журналі доставки — «delivered».

**Гра — рівень не проходиться.**
- Симптом: після перемоги над босом на рівні 3 двері до рівня 4 не відчиняються; у тестувальника відтворюється
  щоразу.
- Гіпотези: (а) подія «бос переможений» не надходить; (б) двері чекають інший прапорець; (в) лічильник ворогів не
  обнуляється — живий хтось, кого не видно.
- Перевірка: вивід у консоль там, де двері перевіряють умову, — `enemies_left = 1`; у сцені ворог, що при появі
  провалився крізь підлогу, живий за межами карти.
- Причина: точка появи одного ворога нижче за колайдер підлоги.
- Виправлення: підняти точку появи.
- Доказ: рівень пройдено тричі з чистого збереження — двері відчиняються, у консолі `enemies_left = 0`; сусідні
  рівні з тими самими ворогами пройдено один раз.

## Доповідь

Коротко: **симптом → причина → виправлення → чим перевірено**. Без переказу пошуків. Власнику — за форматом
«Підсумок власнику» зі скіла `session-end`.
