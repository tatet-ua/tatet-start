# site-analytics

Пути по меню Google и скрипты — [references/google-api.md](references/google-api.md); дашборд, выкладка и
приёмка — [references/dashboard.md](references/dashboard.md).

## Всегда

- Шаги по порядку. Счётчик GA4 — последним: до этого сайт должен открываться по `https://<домен>`, а дашборд — уметь
  показать пустое состояние.
- **Стоп** означает: дождаться, пока студент (или ментор) сделает действие сам или скажет «да» в чате.
- На каждой странице Google сверять учётку в углу с учёткой студента: у людей несколько профилей браузера.
- В Cloudflare студента не входить: записи DNS вносит он, агент даёт точные значения и проверяет.
- Ключи — только через скрипты скила и `with-env.py` набора; файл ключа не открывать, значения не печатать.
  Ключ попал в чат — отозвать и выпустить новый.
- Push и выкладка — после «ок» студента.

## Перед началом

1. Узнать `<домен>`, открывается ли сайт по нему, где код сайта.
2. MCP хостинга менторства: `me` отвечает аккаунтом студента. Нет — **стоп**, нужна ссылка от ментора.
3. `grep -rn -E "gtag|googletagmanager|G-[A-Z0-9]{6,}" <папка сайта>` — счётчик нашёлся: спросить, чей; второй
   ресурс GA4 не заводить.

## 1. Google Analytics 4

Аккаунт, ресурс на `<домен>`, веб-поток `https://<домен>`. Передачу данных в продукты Google не включать.
**Стоп:** соглашение GA4 — «Принять» только после «да» студента. Номер ресурса и `G-…` — в `.env` проекта
дашборда (`GA4_PROPERTY_ID`, `GA4_MEASUREMENT_ID`).

Проверка: поток есть, статус «Данные не поступают».

## 2. Search Console

Ресурс типа «Домен». **Стоп:** студент вносит TXT-запись в своём Cloudflare. Проверка
`nslookup -type=TXT <домен> 1.1.1.1` → видна `google-site-verification=…`, затем «Подтвердить». Сказать студенту:
запись не удалять никогда — без неё пропадут подтверждение и доступ по API.

Проверка: `sc-domain:<домен>` подтверждён.

## 3. Доступ по API

1. Отдельный проект Google Cloud под эту аналитику. **Стоп:** условия Google Cloud принимает студент.
2. Включить Google Analytics Data API и Google Search Console API; каждый проверить в списке включённых — Enable
   срабатывает не с первого раза.
3. Сервисный аккаунт `analytics`, без ролей. **Стоп:** JSON-ключ скачивать после «да» студента; перенос —
   `scripts/sa_to_env.py`.
4. **Стоп:** доступы выдаёт студент руками (агенту не дают проверки Google): GA4 — «Читатель», Search Console —
   «Ограниченный», на почту сервисного аккаунта.

Проверка: `scripts/check_google.py <.env>` → две строки `OK`.

## 4. Дашборд `stats.<домен>`

1. Разведка, только чтение: образец, который назовёт ментор, и свои данные сайта студента.
2. Вопросы студенту по одному, с рекомендацией: экраны первой версии, язык, нужен ли MCP.
3. Спека и план. **Стоп:** код после «ок».
4. Код по этапам, после каждого — `verifier` набора; перед выкладкой `build` зелёный: Prisma и Nuxt ломаются
   только на настоящей сборке.
5. Выкладка через MCP хостинга — порядок в справочнике. Ключ Google на сайт ставит `scripts/put_site_env.py`,
   не `site_env_set`.
6. **Стоп:** студент — `A stats` на IP сервера аккаунта, проксирование выключено (иначе нет сертификата); ментор —
   подключает `stats.<домен>` в карточке аккаунта.
7. Запустить `ga:pull` и `gsc:pull` кнопкой на странице журнала сбора.

Проверка: `curl -sI https://stats.<домен>/` → 302 на вход Tatet Auth; студент и ментор входят; оба прогона `ok`;
все экраны на пустой базе показывают пустое состояние, не ошибку (GA4 отдаёт первый день наутро, Search Console —
через 2–3 дня).

## 5. Счётчик GA4

`gtag.js` с `G-…` только на боевом домене (`<домен>`, `www.<домен>`); `page_view` при переходах без перезагрузки.
Выложить сайт.

Проверка: на `https://<домен>` уходит `g/collect` с `tid=G-…`, на `*.tatet.app` и localhost — нет; переход внутри
сайта даёт ещё один `page_view`; `scripts/check_google.py <.env> --realtime` → активных ≥ 1.

## 6. Приёмка

`verifier` набора по таблице «Приёмка» из справочника дашборда. **Стоп:** итог принимает ментор.
