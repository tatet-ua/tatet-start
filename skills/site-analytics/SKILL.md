# site-analytics — аналитика сайта студента

Путь из шести шагов: Google Analytics 4 → Search Console → доступ к API → дашборд `stats.<домен>` → счётчик на
сайте → приёмка. Счётчик ставится последним, когда сайт уже открывается по своему домену, а дашборд готов показать
первые данные.

Плейсхолдеры: `<домен>` — домен сайта студента без `www`, `<учётка студента>` — его Google-аккаунт,
`<проект GCP>` — проект Google Cloud под эту аналитику, `<студент>` — имя аккаунта студента в менторстве.

## Роли

| Кто | Что делает |
|---|---|
| **Студент** (руками) | работает под своей учёткой Google и в своём Cloudflare; принимает соглашения GA4 и Google Cloud; вносит TXT- и A-записи в DNS; выдаёт сервисному аккаунту доступ в GA4 и Search Console; даёт «да» на скачивание ключа; отвечает на вопросы о составе дашборда |
| **Агент** | даёт точные значения и куда их вписать; нажимает кнопки в браузере только после «да» студента; проверяет каждый шаг командой; пишет код дашборда и выкладывает его через MCP хостинга менторства; ставит счётчик |
| **Ментор** | подключает домен `stats.<домен>` к сайту в карточке аккаунта студента; принимает итог |

## Перед началом

1. Узнать у студента: `<домен>`, открывается ли сайт уже по нему, где лежит код сайта (папка, репозиторий).
2. Проверить, что MCP хостинга менторства подключён: инструмент `me` отвечает и показывает аккаунт `<студент>`.
   Не подключён — сначала ссылка от ментора (стоп, нужен ментор).
3. Проверить, нет ли счётчика в коде сайта: `grep -rn -E "gtag|googletagmanager|G-[A-Z0-9]{6,}" <папка сайта>`.
   Нашёлся — спросить студента, чей это счётчик; второй ресурс GA4 поверх существующего не заводить.
4. Ключи и токены — только в `.env` и через скрипты скила и `with-env.py` набора. Файл ключа и его значения не
   открывать инструментом чтения, не печатать, не писать в чат и в базу знаний.

## Шаг 1. Google Analytics 4

1. Браузер: открыть `analytics.google.com`. **Сверить учётку в правом верхнем углу** с `<учётка студента>` — см.
   ловушку про профили браузера.
2. Аккаунт и ресурс на `<домен>`: часовой пояс и валюта студента, отрасль, цели. Передачу данных в продукты Google
   не включать.
3. **Стоп, нужен человек:** соглашение об условиях GA4 принимает владелец учётки. Агент нажимает «Принять»
   только после явного «да» студента в чате.
4. Веб-поток `https://<домен>` → код `G-…`. Записать номер ресурса (цифры, не `G-…`) и код потока в `.env` проекта
   дашборда: `GA4_PROPERTY_ID`, `GA4_MEASUREMENT_ID`.

**Проверка:** в GA4 «Администратор → Сведения о ресурсе» номер ресурса совпадает с `.env`; в «Потоки данных»
есть поток на `https://<домен>` со статусом «Данные не поступают» — это правильно, счётчик ставится в шаге 5.

## Шаг 2. Search Console

1. `search.google.com/search-console` под `<учётка студента>` → «Добавить ресурс» → тип **«Домен»** (покрывает все
   поддомены и протоколы), ввести `<домен>`.
2. Google покажет TXT-запись `google-site-verification=…`. Агент даёт студенту точные поля: тип `TXT`, имя `@`,
   значение целиком.
3. **Стоп, нужен человек:** студент вносит запись в своём Cloudflare. Агент в аккаунт Cloudflare студента не ходит.
4. Агент проверяет появление записи:
   ```bash
   nslookup -type=TXT <домен> 1.1.1.1
   ```
   В выводе есть строка с тем же `google-site-verification=…`. Нет — подождать пару минут и повторить; через
   полчаса нет — сверить имя записи (`@`, а не `<домен>.<домен>`).
5. Запись есть → «Подтвердить» в Search Console.

**Проверка:** ресурс `sc-domain:<домен>` в списке ресурсов со статусом «Подтверждён». Сказать студенту:
TXT-запись **не удалять никогда** — Search Console периодически перепроверяет её, без записи ресурс теряет
подтверждение, а сервисный аккаунт — доступ.

## Шаг 3. Доступ к статистике по API

Команды, скрипты и разбор ошибок — [references/google-api.md](references/google-api.md).

1. `console.cloud.google.com` под `<учётка студента>` → новый проект `<проект GCP>` (отдельный под эту
   аналитику, не общий рабочий). **Стоп:** условия Google Cloud при первом входе принимает студент.
2. «APIs & Services → Library» → включить **Google Analytics Data API** и **Google Search Console API**.
   После каждого «Enable» открыть «Enabled APIs & services» и убедиться, что API в списке: кнопка иногда не
   срабатывает с первого раза, и тогда запросы дают 403 `SERVICE_DISABLED`.
3. «IAM & Admin → Service accounts → Create»: имя `analytics`, роли в проекте не выдавать.
4. «Keys → Add key → JSON». **Стоп:** скачивание файла ключа — после «да» студента. Скрипт `scripts/sa_to_env.py`
   переносит поля в `.env` проекта дашборда, а файл ключа — в `secrets/` (в `.gitignore`).
5. **Стоп, нужен человек:** выдачу доступов делает студент руками — агенту это не дают проверки безопасности
   Google. Агент даёт почту сервисного аккаунта `analytics@<проект GCP>.iam.gserviceaccount.com` и путь:
   - GA4: «Администратор → Управление доступом к ресурсу → + → Добавить пользователей» → почта → роль
     **«Читатель»**, уведомление снять;
   - Search Console: ресурс `sc-domain:<домен>` → «Настройки → Пользователи и разрешения → Добавить
     пользователя» → почта → **«Ограниченный»**.

**Проверка:** `python "<папка скила>/scripts/check_google.py" "<проект дашборда>/.env"` печатает две строки `OK`:
GA4 `runReport` и `sc-domain:<домен>` в списке ресурсов Search Console. Нули в GA4 на этом шаге — норма.

## Шаг 4. Дашборд `stats.<домен>`

Разведка, вопросы, состав первой версии, выкладка и приёмка подробно — [references/dashboard.md](references/dashboard.md).

1. **Разведка** (агент, только чтение): дашборд-образец, который назовёт ментор, и специфика сайта студента —
   какие свои данные и действия посетителей у него есть и что из этого видно в GA4.
2. **Вопросы студенту по одному**, с рекомендацией: состав первой версии, язык интерфейса, нужен ли MCP-сервер.
3. **Спека и план** — короткий документ в проекте дашборда. **Стоп:** код пишется после «ок» студента.
4. **Код по этапам**, после каждого этапа — проверяющий с чистым контекстом (агент `verifier` набора).
   Сборка, тесты и типы зелёные до выкладки.
5. **Выкладка через MCP хостинга менторства** — порядок вызовов в справочнике, раздел «Выкладка». Ключ сервисного
   аккаунта в переменные сайта ставит скрипт, не `site_env_set`.
6. **Свой домен.** Студент в своём Cloudflare заводит `A stats` на IP сервера аккаунта, **без оранжевого облака**:
   с проксированием хостинг не выпустит сертификат. **Стоп, нужен ментор:** домен `stats.<домен>` к сайту
   подключает ментор в карточке аккаунта; статус должен дойти до «работает».
7. **Первая сборка данных:** запустить `ga:pull` и `gsc:pull` кнопкой ручного запуска на странице журнала сбора;
   в журнале оба прогона `ok`.

**Проверка:** `curl -sI https://stats.<домен>/` → 302 на вход Tatet Auth; студент и ментор входят и видят экраны;
`site_status` — сайт работает; журнал сбора показывает прогоны. Нет данных — экраны показывают пустое состояние,
не ошибку.

## Шаг 5. Счётчик GA4 на сайте

Только когда сайт размещён и открывается по `https://<домен>`.

1. Добавить в код сайта тег `gtag.js` с кодом `G-…` из шага 1. Счётчик включается **только на боевом домене**:
   `location.hostname` равен `<домен>` или `www.<домен>`; dev, превью и `*.tatet.app` не считаются.
2. Переходы без перезагрузки страницы (SPA) должны отправлять `page_view`: по смене маршрута в коде либо
   включённой настройкой потока GA4 «Расширенная статистика → просмотры при изменении истории».
3. Выложить сайт (`site_deploy` или push, как у сайта заведено).

**Проверка:**
- в браузере на `https://<домен>` уходит запрос `.../g/collect?...tid=G-…` (вкладка сети или
  `read_network_requests`); на адресе `*.tatet.app` и на localhost — не уходит;
- переход по ссылке внутри сайта даёт ещё один `g/collect` с `en=page_view`;
- визит виден в отчёте реального времени: `check_google.py` с ключом `--realtime` → активных пользователей ≥ 1.

## Шаг 6. Приёмка снаружи

Проверяющий с чистым контекстом (`verifier` набора), кода не видел, на проде только читает. Список проверок — в
[references/dashboard.md](references/dashboard.md), раздел «Приёмка»: без входа всё закрыто, обходы путей
закрыты, адреса OAuth и MCP ведут себя как задумано, порт базы снаружи закрыт. Итог принимает ментор.

| Шаг 1 | студент | «да» на соглашение GA4 |

| Шаг 3 | студент | условия Google Cloud; «да» на скачивание ключа; доступы в GA4 и Search Console |

## Ловушки

- **Чужая учётка в браузере.** У людей несколько профилей браузера с разными Google-аккаунтами. На каждой странице
  GA4, Google Cloud и Search Console сверять учётку в углу с `<учётка студента>` и выбирать нужный профиль браузера,
  а не первый попавшийся. Ресурс, заведённый не под той учёткой, потом переносить долго.
- **Ключ попал в чат.** Удалить этот ключ в Google Cloud («Service accounts → analytics → Keys») и выпустить новый.
- **Данных ещё нет.** GA4 отдаёт первый полный день только на следующее утро, Search Console — с задержкой 2–3 дня.
  Экраны показывают пустое состояние, сбор пишет `ok` с нулём строк, а не падает. До приёмки пройти все экраны на
  пустой базе: ответ без данных проверять до чтения его полей.
- **Первая сборка падает.** Prisma и Nuxt проверяются только настоящей сборкой: `dev` этого не ловит. Перед
  выкладкой — `build` локально; упало на хостинге — читать `site_logs`, а не гадать.
