# tatet-start

## Що це
Спосіб роботи з Claude Code від менторства Tatet. Для студентів будь-якої сфери: тексти і SEO, ігри, сайти, офісна
робота. Програмувати не обов'язково. Набір тримається на чотирьох опорах:
- **база знань поза чатом** — чат одноразовий, а що зроблено і що вирішено, лишається в базі й читається наступною сесією;
- **агентний режим з технічними межами** — велику роботу сесія ділить між агентами, і перевіряльник фізично не може правити те, що перевіряє;
- **дошка проєкту зі шляхом** — картки задач і смуга від старту до фінішу, яку видно одним поглядом;
- **склад ключів, які модель не бачить** — токени лежать у файлі, команди отримують їх через скрипт, у чат значення не потрапляють.

Нове в набір і на робоче місце додається, коли вперлися в конкретну проблему, а не про запас.

## Потрібно
Claude Code. Ще набору потрібні Python 3.10+ і git — якщо їх немає, агент скаже, що поставити, коли ти попросиш
налаштувати набір.

## Встановлення
Два варіанти, результат однаковий. Термінал знати не обов'язково.

**Без терміналу** — усе в чаті Claude Code:
1. Набери `/plugin install tatet-start --marketplace tatet-ua/tatet-start`. Claude Code попросить підтвердити, що
   додає каталог `tatet-ua/tatet-start`, і відкриє картку плагіна — вибери «Install for you». Ця команда одним
   рядком є в Claude Code з версії 2.1.275; у старішій набери по черзі `/plugin marketplace add tatet-ua/tatet-start`
   і `/plugin install tatet-start@tatet-start`.
2. Напиши в чаті «налаштуй tatet-start» (або «налаштуй набір»). Агент спитає літеру диска, перевірить Python і git
   і словами пояснить, чого бракує, а потім сам запустить установник: той створить `<диск>:/project/DevOps` і
   `<диск>:/project/llm-wiki`, змінні, блок ритуалу і команду `board` (докладно — нижче).
3. Перезапусти Claude Code: так підхопляться змінні й команда `board`.

**Через термінал** — три команди по черзі:
```bash
claude plugin marketplace add tatet-ua/tatet-start
claude plugin install tatet-start@tatet-start
python "<шлях до плагіна>/scripts/setup.py"
```

Шлях до плагіна: `~/.claude/plugins/cache/tatet-start/tatet-start/<версія>/`, де `~` — твоя домашня папка. Потім
перезапусти термінал і Claude Code.

**Що робить установник** (в обох варіантах однаково). Питає одне: на Windows — літеру диска, на macOS і Linux —
підтвердити `~/project`. Далі він:
- створює `<диск>:/project/DevOps` (склад ключів `.env` і зразок `.env.example`) і `<диск>:/project/llm-wiki` (база
  знань зі схемою, `git init`); наявні файли не перезаписує, `.env` не чіпає ніколи;
- пише змінні `TATET_WIKI`, `TATET_DEVOPS`, `BOARD_DIR`, `BOARD_PORT` у `env` файлу `~/.claude/settings.json`
  (решту файлу зберігає, перед записом робить резервну копію);
- дописує блок ритуалу сесії в `~/.claude/CLAUDE.md` між мітками `<!-- tatet-start:begin -->` і
  `<!-- tatet-start:end -->`;
- створює команду `board` в `~/.local/bin` (на Windows — `board.cmd` і цю папку в PATH користувача) і перевіряє,
  що дошка запускається.

Що треба зробити руками, установник напише в кінці (у чаті це перекаже агент). Для запуску з терміналу є ключі:
подивитися наперед, нічого не змінюючи, — `--dry-run`; папка `project` в іншому місці — `--root <шлях>`; без
питань — `--yes`.

## Сесія: початок і кінець
**Початок.** Відкрий Claude Code у папці проєкту (з терміналу — `claude` у цій папці). Блок у глобальній
інструкції і скіл `session-start` змушують агента до відповіді по суті прочитати `index.md` бази й останній лог проєкту з
`raw/sessions/` (логу немає — сторінку проєкту у `wiki/projects/`). Перша відповідь — три частини: на чому
зупинились, один наступний крок і готовий запит у блоці для копіювання в нову сесію. Проєкт новий — агент так і
скаже і спитає, що робиш сьогодні. Перший день — своя справжня задача (стаття, рівень гри, сторінка, лист), а не
навчальна. Відповідь на робочу задачу агент починає позначкою `*→ скіл: <назва>*` або `*→ без скіла*`: видно, що
спрацювало. Скіл не той — скажи «не той скіл» або «візьми debug-first».

**Кінець.** Скажи «завершуємо» або виклич `/tatet-start:session-end`. Також варто після кожного суттєвого
результату: лог пишеться, лише поки розмова жива. Що станеться:
1. якщо проєкт на дошці — агент `acceptance-verifier` приймає виконані картки;
2. лог `raw/sessions/РРРР-ММ-ДД-<проєкт>.md`: старт, хід, граблі, рішення, стан, беклог, готовий запит;
3. проковтування у вікі (`kb-ingest`): оновлюються сторінки `wiki/`, `index.md`, `log.md`;
4. локальний коміт бази; push, якщо в бази є віддалений репозиторій, — тільки після твого «ок»;
5. дошка і шлях проєкту, якщо проєкт на дошці.

**Як влаштована база** (`<диск>:/project/llm-wiki`, схема — її `AGENTS.md`):
- `raw/` — джерела, не правляться ніколи: `sessions/` (логи), `specs/` (специфікації), `meetings/` (листування,
  рішення людей), `docs/` (документи, вивантаження, старі нотатки);
- `wiki/` — сторінки, які пише тільки агент через проковтування: `projects/`, `services/`, `decisions.md`,
  `patterns/`, `infra.md`; кожне твердження посилається на джерело в `raw/`;
- `index.md` — хаб, рядок на проєкт; `log.md` — рядок на кожне проковтування.

Хочеш змінити факт у вікі — не правиш сторінку, а кладеш файл у `raw/` або кажеш агентові в сесії, і це йде через
лог. Питання до бази ставиш агентові словами: він іде `index.md` → сторінка → джерело. Цінна відповідь, якої у
вікі немає, кладеться в `raw/docs/` і проковтується. Раз на тиждень — «перевір базу знань» (`kb-lint`): звіт
`raw/sessions/РРРР-ММ-ДД-lint.md`, виправлення — проковтуванням цього звіту.

## Агентний режим
**Вмикається сам**, коли задача велика: нова частина проєкту за затвердженим планом; правка від п'яти об'єктів
або двох незалежних частин (текст і розмітка, два розділи сайту); аудит, дослідження, розбір документа, довгий лог;
кілька незалежних задач одним повідомленням. Не вмикається на дрібній правці, у розмові і під час налагодження,
поки причину не знайдено. **Вручну** — `#агенти`, «агентний режим», «через агентів». **Вихід** — `#сам`.

Що ти побачиш:
1. першим рядком позначку `*→ агентний режим: #агенти*` або `*→ агентний режим: авто: <причина>*`;
2. «як я зрозумів» — чотири питання: що тут об'єкт роботи, що джерело правди, яка перевірка з наперед записаним
   очікуванням, що незворотне;
3. таблицю агентів «задача · тип · модель · чому · рубіж» (рубіж — читає, править чи перевіряє) і що повернеться;
4. запуск; наприкінці таблицю «заявлено · виміряно · вердикт» і рядок витрати агентів із журналу.

Не згоден із таблицею — напиши, що змінити, або `#сам`. Режим витрачає токенів помітно більше, ніж робота в одному
вікні (оцінка — у два-три рази), тому на дрібниці сам не вмикається.

Типи агентів і чого вони не можуть технічно:
- `scout` (розвідник) — з'ясовує, де що лежить і як зроблено в оригіналі; лише Read, Grep, Glob, WebFetch: ні
  запису, ні команд;
- `verifier` (перевіряльник) — звіряє результат із критерієм задачі, звіт автора не читає; Write і Edit немає;
- `rules-reviewer` (рев'юер правил) — звіряє зміни з інструкцією проєкту, брифом, регламентом; Write і Edit немає;
- `collector` (збирач) — зводить звіти віяла агентів в одну таблицю; лише читання, без команд;
- `acceptance-verifier` — приймає картки дошки; Write і Edit немає, на живому сайті тільки читає (GET, HEAD).

Виконавець, який править об'єкти, — звичайний агент зі списком того, що йому можна чіпати. Де в агента є Bash,
після прогону сесія дивиться `git status --short`: будь-яка зміна — порушення. Незворотне (публікація, відправлення,
деплой, оплата, видалення) робить тільки сесія і тільки після твого «ок».
Як режим зібраний із модулів — [docs/agent-mode.md](docs/agent-mode.md).

## Дошка проєкту
У перший день дошка не потрібна: сесія працює і без неї. Підключай, коли з'явився перший проєкт, який ведеш
кілька сесій: скажи «додай проєкт на дошку», і агент перенесе проєкт на дошку та заведе шлях; далі «дошка проєкту» і «шлях проєкту» показують стан. Інші
слова, на які спрацьовує скіл: «онови дошку», «що чекає на мене», «візьми задачу з дошки», «смуга прогресу».

Відкрити сторінку дошки: напиши «запусти дошку» (або «відкрий дошку») — агент запустить сервер і дасть адресу
http://127.0.0.1:8790. Через термінал — `board serve` (порт — `BOARD_PORT` або `--port`); сервер працює, доки
відкрито термінал. Ти рухаєш картки мишею, агент — командами `board`. Інтерфейс дошки поки російський.

Колонки: «Бэклог» → «Новая» → «В работе» → «На согласовании» → «Выполнена» → «Завершена»; архів — «Отложена» і
«Отменена». У «На согласовании» агент ставить картку, коли йому потрібне твоє рішення. Вище «Выполнена» агент
картку не ставить: у кожної виконаної є доказ і критерій «що виконати → що має вийти». Картки з прийманням
«проверяющий» приймає агент `acceptance-verifier` пачкою наприкінці сесії: сам виконує критерій і переносить у
«Завершена» або повертає в «В работе» з позначкою «на доработку». Картки «принимаю сам» (вигляд, тексти, гроші,
договори) приймаєш ти на сторінці. Будь-яку прийняту картку можеш повернути з коментарем — наступна сесія
розбере її першою.

Шлях проєкту — смуга для одного погляду з телефона: **старт** (дата і подія), **спринти** (відрізки з умовою
«закрито, коли …»), **фініш** (результат однією фразою), **туман** (що видно далі, до п'яти рядків). Шлях
збирається сам: старт — з першого джерела проєкту в базі, фініш — із мети в `AGENTS.md` проєкту чи специфікації,
спринти — з етапів плану, туман — з беклогу логу. Фініш, відкриття і закриття спринту затверджуєш ти словом: агент
питає одним рядком у кінці відповіді, наприклад «шлях: затвердити фініш „…“ / відкрити спринт s2 / закрити s1 —
відповідай „так“ або виправ». Без твоєї відповіді в цій сесії нічого не затверджується. Сторінка шляху
перезбирається в кожному лозі (`board progress`) і лежить у `boards/progress/<проєкт>.html` бази.

## Склад ключів
Усі ключі й токени — у `<диск>:/project/DevOps/.env`. Вписуєш їх туди руками, у чат не вставляєш ніколи. Новий
ключ: агент називає ім'я змінної і де його видають, ти вписуєш значення.

Модель значень не бачить. Хук `guard-env` блокує читання файлу і команди, що виводять його вміст. Скрипт
`with-env.py` з папки `scripts` плагіна підставляє ключі командам, а у виводі замінює будь-яке значення з файлу
(від шести символів) на `‹ЗМІННА›`. Ці команди виконує агент, тобі їх вводити не треба:
- імена змінних — `python "<шлях до плагіна>/scripts/with-env.py" --names`;
- чи задані — `--has ІМ'Я [ІМ'Я …]`;
- команда з ключем — `--only ІМ'Я -- <команда>` (кілька — через кому).

Папку `DevOps` не перейменовуй: захист знаходить склад за назвою папки.

## Налагодження від причини
Скіл `debug-first`: симптом → гіпотези → перевірка → причина → виправлення → доказ; спершу шукає в базі, чи не
траплялося таке вже. Для коду, статей, листів і ігор. Спрацьовує на «не працює», «помилка», «впало», «баг».

## Стек для внутрішніх інструментів
За бажанням, для тих, хто пише код. Скіл `stack-vue`: Nuxt 4, Tailwind v4, Prisma 6, компоненти tatetUI
(https://ui.tatet.net, копіюються файлами). Адмінки, панелі керування, дашборди — лише tatetUI і правила скіла;
лендінги й публічні сторінки — на розсуд автора, правила адмінки на них не діють. Спрацьовує на «потрібна адмінка»,
«панель керування», «дашборд», «на tatetUI».

## Оновлення
**Без терміналу:** напиши в чаті «онови набір». Агент оновить плагін, знову запустить установник і скаже, коли
перезапустити Claude Code.

**Через термінал** — три команди по черзі, потім перезапусти Claude Code:
```bash
claude plugin marketplace update tatet-start
claude plugin update tatet-start@tatet-start
python "<шлях до плагіна>/scripts/setup.py"
```

Після оновлення в шляху до плагіна інша `<версія>`, тому установник запускається знову: він переписує команду
`board`. Повторний запуск нічого не дублює.

## Видалення
У чаті: `/plugin` → Installed → tatet-start → Uninstall; у терміналі: `claude plugin uninstall tatet-start@tatet-start`. Руками прибрати: обгортку `board` у `~/.local/bin` (на Windows — `board.cmd` і цю папку з PATH користувача), чотири змінні `TATET_WIKI`,
`TATET_DEVOPS`, `BOARD_DIR`, `BOARD_PORT` у `env` файлу `~/.claude/settings.json` і блок між мітками
`tatet-start` у `~/.claude/CLAUDE.md`. Папки `project/llm-wiki` і `project/DevOps` — твої дані, їх ніхто не видаляє.

## Якщо ти вже проходив курс
Став так само. Свої нотатки й документи поклади файлами в `llm-wiki/raw/docs/` і в сесії скажи «проковтни» з
назвою файлу — по одному. Файли з ключами чи паролями в `raw/` не клади. Установник не перезаписує наявні файли й
папки, а в `~/.claude/CLAUDE.md` лише дописує свій блок між мітками, решту інструкції не чіпає.
